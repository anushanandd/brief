# Architecture

> This describes the code as it stands. Why the invariants exist is in [PRINCIPLES.md](PRINCIPLES.md); this file shrinks as the planned storage changes replace what it describes.

Brief is a single-user macOS app built with Tauri. Rust owns everything that touches money or secrets: provider access, credentials, calculations, and durable state. React owns presentation and view state. Nothing runs on a server.

```text
Plaid · SnapTrade · Alpaca · SEC EDGAR · Alpha Vantage · CNBC RSS
                 │  read-only, retried, bounded
                 ▼
      providers ──► staged provider caches
                 │
                 ▼
      financial_engine: typed records, Decimal math
                 │
                 ▼
      storage: validate, then commit the state and its changeset
               (the change log) in one SQLite transaction
                 │  on every read
                 ▼
      annotations + settings ──► insights
                 │  Tauri IPC
                 ▼
      types generated from Rust ──► React Query ──► routes
```

Live market prices travel a separate path and may overlay a committed snapshot, but never rewrite it.

## Invariants

- **Secrets:** credentials and provider tokens live only in macOS Keychain. Logs, diagnostics, fixtures, and tests never contain credentials, tokens, raw provider messages, or real financial data.
- **Atomic refresh:** a refresh is staged, bounded by one 120-second deadline, validated, and committed in a single transaction. Any failure leaves the previous snapshot and caches usable.
- **Plaid paging:** cursor and page changes stay temporary until pagination and the matching balance request both succeed.
- **No invented values:** missing, unsupported, or non-USD values stay unavailable. They are never converted to zero, and an incomplete total says so.
- **One policy, in Rust:** transaction classification, forecasts, statement cycles, benefit rules, attention items, period changes, and Data health are computed in Rust. React formats them and never reimplements them.
- **Determinism:** results depend only on the snapshot, annotations, settings, and the local calendar day. Each projection stores its calendar date so a timezone change can't move a month boundary. The one exception is the investment summary, which also reads the market sessions saved for its period: a closed session's layers stay as they were computed.
- **Settings that change results** (spending account and other spending cards, account names, start and closed dates, account details (website, stated APY), manual accounts, benefit visibility, the billed Plaid products, background refresh, notifications, the Brief calendar, the card product each extra card is tracked as, the tax profile, account tax treatments, retirement details (birth year, planned costs, earlier Roth contributions, and the tax year each IRA deposit counts toward), people, and who went on each trip) live in the finance database, never in renderer storage.
- **Spending account by ID:** statements and Platinum benefits use the saved account ID, never provider ordering. Spending may cover one account or every USD account, and never treats another card as the saved one.
- **Billed calls are opt-in:** Plaid live balances, Liabilities, Investments Transactions, Recurring Transactions, and Statements never run on an ordinary or background refresh unless the user chose them. Each is its own Plaid charge, and its Settings row says so.
- **The log is the truth:** every write to the finance state is one `Change` (`storage/change.rs`): a refresh carries what the providers returned and the clock it was projected at; a statement import, an edit, or a settings save carries itself; a checkpoint carries a whole state. The write applies it with `change::apply` and saves the result together with a changeset (`database/changesets.rs`) holding the change and the SHA-256 of the state it produced, in one SQLite transaction, so evidence Plaid replaces (a pending charge, its tip, a dropped hold) is kept. Replay applies the same changes with the same function from the latest checkpoint and must reproduce the saved tables; a launch checks this in the background through its own connection, and Data health reports a difference. Checkpoints start the log (what a database already held), follow a restore, erasure, or a new calculation version (earlier changes would project differently under new code), and come every 50 changes. Changesets name their parent, this database's device id, and their sequence number there, so a second device could merge logs later. Triggers refuse updates and deletes. Brief reads what the log holds, and the saved tables are its cache (`change::authoritative`): opening hashes them, and they stand when they match the state the latest changeset recorded, so a launch costs one hash, not a replay. Tables that don't match never reach a reader. The log is replayed from its latest checkpoint with the current code and the tables are rewritten from the result; when that code reads the log differently than it recorded (an update that added a field or changed a calculation), the result is saved as a checkpoint so later opens compare cleanly. Only a log that can't be read fails the open, into recovery. A backup is read and restored by its own log the same way. `ledger_events`, the per-record log of versions 17 to 19, is no longer written and keeps its rows. Erasure drops both; a restore installs the backup's log and keeps the replaced database as a retained copy.
- **Calendar:** with full Calendar access, Brief writes only to the calendar named "Brief" (the user's own, or one Brief made where none existed, since Google accounts don't let apps make calendars), and only events carrying its reference for an agenda item (a kind and a hash of the item's id, never the id itself) in their `brief://calendar` link or the last line of their notes (Google may drop the link), matched to `agenda` after each refresh and settings save and once a day; an event it didn't make, or one that ended more than 30 days ago, is never changed. The user's other events are read for the Calendar page and trips, never saved, logged, or used by insights.
- **Apple Intelligence has no authority:** in answers it may quote only results from read-only Rust tools. It cannot calculate or change finance data, and it writes nothing in the investment summary. Each answer is returned with the tool queries that ran, so its figures can be checked; Rust lists any figure in the answer that none of them returned, and an answer the tools couldn't support is marked unavailable rather than failing. A query pinned to Home is rerun by Rust from saved data, without the model.
- **Brief never infers a cause:** the investment summary's reasons are publishers' headlines, quoted as published with the publisher, time, and link, and shown only when a headline names a holding that led the day and says it moved that way, or is a market wrap saying the market moved its way.

Only `finance-state.sqlite3` and `documents.sqlite3` are authoritative. The other databases are disposable caches. Their failure never affects finance data, and recovery ignores them. The app-data directory is `0700` and database files are `0600`, but SQLite files are not encrypted; only document originals are.

**Documents** (`documents/`) are the user's own files: pay statements, tax forms, statements, and exports. Each original is sealed with AES-256-GCM under one random key kept in Keychain, its id (the SHA-256 of its bytes) bound in, and stored in `documents.sqlite3`, which is only ever added to or pruned, so commits never copy it; what Brief read lives in the finance database and is backed up with it. Reading happens on the Mac through the native bridge: a PDF's text layer, and Vision where columns matter or there is no text. Readers are deterministic and data-driven (`forms.json`, `payslip.json`); each checks itself (net pay, copies of a form agreeing, a statement's balances), and every figure stays the user's to confirm, a typed value surviving any later reading. A reading records its reader's version (`READER_VERSION`); raise it when a reader changes what it reads, so earlier readings are offered for reading again. Apple Intelligence writes each document's summary in the background (`document_summaries.rs`) from its text alone; a summary is kept only when every figure in it is printed in the document, and it never feeds a calculation. Brief's viewer decrypts an original in memory; only Open in Preview writes a private copy. A statement PDF that balances becomes CSV for the statement importer, added to an account only when the user asks; reading one already in history again replaces its rows only when they keep the same days and amounts, so only descriptions change and confirmed rows stay confirmed. A backup carries the sealed originals and, given a passphrase, the key sealed under it with Argon2id, so another Mac re-seals them with its own key; erasure removes the originals but keeps the key, so earlier backups still open.

## Refresh and commit

`refresh_finance_snapshot` runs once at a time:

1. Take the refresh lock and start the 120-second deadline.
2. Read credentials from Keychain and copy the committed revision and caches.
3. Fetch each provider into temporary state. A provider failure keeps its last usable cache and adds a notice. A provider with no cache can't be invented.
4. Stage the candidate caches against the original revision.
5. Project with `financial_engine::project`. Malformed provider records are skipped with a notice.
6. Validate the snapshot: identifiers, references, currencies, totals, and histories.
7. Back up the database, then replace the snapshot and caches and append the refresh's changeset in one SQLite transaction.
8. Record a redacted sync diagnostic separately, so diagnostics can never block a valid commit. It holds each provider's requests, retries, bytes, and time, each stage's time, the snapshot's size, and how many transactions changed: counts and timings, never names or amounts.

Provider specifics:

- **Plaid** balances come from Plaid's cached `/accounts/get`. The billed `/accounts/balance/get` runs only on an explicit live-balance refresh. Reconstructed balance history claims the requested 730-day window only after Plaid reports its historical pull complete; until then it starts at the earliest transaction received. Transactions use Plaid's v2 category taxonomy, and an Item cached under another taxonomy is rebuilt once from a fresh cursor. When enabled, `/liabilities/get` supplies statement dates; its failure is a notice, never a failed refresh. Response bodies are capped at 32 MiB, and safe reads retry at most twice.
- **Plaid transactions** are requested with the institution's original descriptor. A cache saved in an older request format (`PLAID_TRANSACTION_FORMAT`) is rebuilt once from a fresh cursor, as a taxonomy change is.
- **Plaid Statements** (opt-in per bank connection, added through Link's update mode so the item and its accounts stay, and offered only where Plaid lists Statements among the institution's products and the connection holds a checking or savings account) saves the bank's own PDFs for checking and savings accounts, each checked against Plaid's SHA-256 before it is kept (`bank_statements.rs`). After a committed refresh, a background check lists each connection's statements at most daily and downloads new ones; once a month it asks Plaid to fetch newly posted ones, which Plaid reports only by webhook, so a later check lists them. Brief keeps the files and reads no figures from them. Opening one writes a private copy in the app-data directory, replaced on the next open.
- **Plaid Investments Transactions** (opt-in) reads each investment Item's last 24 months of trades, dividends (qualified or not, when the institution says), fund distributions, fees, and contributions. Its failure is a notice; holdings still commit. Gains are estimated only for accounts whose whole available history was read.
- **Plaid Recurring Transactions** (opt-in) saves Plaid's streams. A series every covering stream reports inactive and tombstoned is no longer forecast; Brief's own policy still decides everything else.
- **Alpaca corporate actions** (splits and cash dividends for every held or traded symbol) are fetched once a day and committed with the refresh, because splits change lots and gains. A position's pre-split trades are restated only when the restated history explains the shares held and the recorded one doesn't, so a broker's already-adjusted history is never adjusted twice.
- **Institution logos** are looked up on Logo.dev by exact domain, from the website Plaid (`/institutions/get_by_id` with optional metadata, once per connection) or SnapTrade (each brokerage login) reports, only when logos are enabled. Without one, an account shows its type's icon.
- **SnapTrade** accounts are valued from cash plus positions. The provider-reported total is evidence only. A holdings sync older than 30 minutes keeps the combined history provisional. An account's daily history is rebuilt from its records (`performance.rs`): starting from today's shares and cash, each earlier day undoes the cash movements and the split-restated share changes recorded after it, and prices the shares then held at that day's Alpaca close (fetched for every symbol the account holds or traded). Before the first recorded activity nothing changed, so the rebuild reaches back to the provider's first day while the account held anything. The provider's balance history, which can be wrong by the size of a transfer, is used only when the records don't explain the account (a day with fewer than no shares, or shares Alpaca can't price) or activity didn't load; it reaches back at most a year and skips days, so a skipped day carries the prior balance plus known deposits and withdrawals. Shares a stock plan allocates arrive with no cash amount; they count as a deposit worth that day's Alpaca close, and without a close they are left out.

Net worth history is the sum of these histories, with the net worth Brief saw at each complete refresh in place of the estimate. An observation that strays from that day's estimate beyond both $100 and 2% yields to it, since a refresh can catch one side of a transfer before the other; `historyCheck` still counts the gap, which Data health reports.

Each refresh that read providers compares the previous snapshot's transactions with the new ones (`financial_engine::refresh_changes`): a charge that posted for a different amount than its pending one, one that vanished, one the bank amended, and new ones are kept as transaction changes (the latest 500), while activity dated more than ten days before the previous refresh is counted as arriving late. For each Plaid cash and card account, the balance effect of those changes is saved with the account's movement as what explains it. Data health reports a balance whose unexplained part has stayed through two refreshes and grew within a month, and a card payment from a tracked bank account that isn't paired with a credit on a tracked card.

The transaction policy pairs each transfer between two of your accounts once (`pair_transfers`), and both legs carry the other's id as `transferPairId`: an equal and opposite posted leg in another account within five days, the nearest by date, each leg pairing once. Net-worth history, Data health's card payments, and the renderer read those pairs and never match legs themselves. Net-worth history counts a pair once, even while its legs post on different days. When a provider files one leg as income, spending, or Other, an equal and opposite transfer leg makes it a transfer too, unless its category was chosen by hand or by rule. Cash withdrawals, payment-app money, and someone else's money never pair. A total's history (net worth, the combined brokerages, an account's holdings) starts at the earliest history among its parts, and each part counts from its own first point; a part known only by today's value leaves the total without history, since it would enter as a jump.

**Imported statements** (CSV or XLSX exports, `statements/`) fill an account's history from before its provider's first reported activity. From that day on, a Plaid cash or card account's statement is the issuer's final record and is reconciled against Plaid (`statements/plan.rs`, saved as `statementReconciliation`): each row is paired with the Plaid transaction it describes (same amount within a few days, then closest and most alike), a row describing one at another amount marks the amounts as disagreeing, and Plaid transactions well inside a statement's days that it doesn't list are reported. A row Plaid never reported joins history only after the user confirms it, and only until Plaid reports it, so it is never counted twice; Data health lists what is left. A statement whose own total and balances can't settle its sign (a card export listing charges as positive) takes it from the Plaid rows it matches, or else from the account's other statements. Other accounts take the provider's own days as reported. The saved file is authoritative and is parsed again on every projection, so which rows count follows the provider's current history. Rust finds the table using `statements/vocabulary.json`, checks the rows against the statement's printed total and running balances, and refuses a file whose total disagrees. A row a provider reports a few days later is matched and not added; rows two overlapping statements share count once, while identical rows within one statement all count. Rows for a Plaid cash or card account are projected as Plaid records, so they share Plaid's categories, the transaction policy, and the reconstructed balance history, which then reaches back past Plaid's window. An import or removal re-projects saved provider data without the network and commits like a refresh.

Refresh triggers: a visible app refreshes silently when the snapshot is at least an hour old. Opt-in background refresh (`background.rs`) keeps the app alive with its window hidden and refreshes when the snapshot is at least 20 hours old. While background refresh is on, a menu bar item reopens, refreshes, or quits the hidden app. With notifications also on, a background refresh posts at most three notifications for new needs (payment due, cash shortfall, credit expiring, a card closing its statement with a high share of its limit in use, a possible duplicate charge), once each per run; they can appear on a locked screen, so they never contain an amount.

## Transactions and insights

Provider categories come from `financial_engine/categories.json`, a versioned map from Plaid's primary and detailed codes to about twenty top-level categories, an optional `subcategory` label (shown only when Plaid's confidence is not `UNKNOWN`), and a transaction kind. When a provider category applies, that kind decides the transaction's meaning; the name and text policy covers refunds, unknown codes, and manual or rule categories. A positive issuer statement-credit descriptor (the benefit rules' credit descriptors, or Amex/Platinum "… Credit"/"… Reimbursement") is always a credit, because Plaid files these under the benefit's spending category, a transfer, or a fee.

A card purchase's merchant, presence, and place are read from every record of it, trusted in this order: the card issuer's imported export, the bank's descriptor, then Plaid. A statement export's issuer columns (address, city and state, postal code, country, the issuer's category, and the fuller name and phone in its details; nothing else from the details, such as passenger records) attach to the Plaid transaction its row describes, matched or at another amount, and to rows Plaid never reported; since saved files are parsed on every projection, each import adds them to every transaction it covers, and Data health lists a card's purchases since its last export once a statement cycle has passed. `merchants.rs` decides, on each read, whether the cardholder was there (`presence`: remote for a brand-prefixed descriptor such as `EXAMPLE *PRODUCT`, a remote processor, words such as ONLINE, a web address, the issuer's category, or an airline; in person otherwise for an in-store purchase or a card-present processor), and keeps Plaid's merchant name unless the records contradict it: another brand where Plaid's own location names another city or Plaid didn't recognize the merchant, or another number. The replaced name stays as `providerMerchant`. Processors, wallet and bank prefixes, brand abbreviations, and the remote words and categories live in `merchants/descriptors.json`.

Every transaction made in person carries a resolved `place` beside the provider's own `location`, which is never changed; a remote purchase has none, since where it bills from says nothing about where the cardholder was. The issuer's street address leads, unless the descriptor names another city or state, which marks a billing office (an online order's, a head office's); a purchase through a processor that prints its own office (a vending machine's) has no place. `places.rs` reads the bank's descriptor next: card descriptors end in the merchant's city and a state, province, or country code, often run together with a truncated merchant name, so the city is the longest known name ending the text, and a code with two readings (DE, CA, NL) takes the reading whose city matches. A bank's own trailer ("Transaction Date : …") is ignored. Issuers print some stores abroad with no code at all, so an in-store purchase's descriptor may also end with a city no other place shares a name with (and that has a population: the gazetteer also lists towns GeoNames gives none, such as boroughs of merged cities, only for descriptors with a code). Plaid's location is the address of the merchant Plaid named, so once the records contradict that merchant it isn't used. Providers send no location for most purchases abroad and sometimes a chain's corporate address, so the descriptor's city wins; the provider's exact coordinates are kept only when it names the same city or street address, and its location fills in only when the descriptor names no city. A web address in a descriptor names the merchant's site, so it yields a state at most. City names and coordinates come from GeoNames (CC BY 4.0, credited in Settings), bundled as `places/cities.tsv.gz` and rebuilt with `scripts/build-places.py`.

Only when the user asks (Settings or the palette's Find places) does Brief go online for places: `places::overture` reads Overture Maps' monthly places release (CDLA-Permissive-2.0, Apache-2.0, CC0, credited in Settings) straight from its public GeoParquet files, downloading for each city with unsearched purchases only the row groups that meet the city's area and only the columns Brief keeps. Only the area leaves the Mac, never a merchant's name. `places::cache` keeps, per purchase key, just the candidates near it in `places.sqlite3`, searched again after 180 days. On each read, `places::matching` matches a purchase made in person to a business only when exactly one fits: at the issuer's street address, the one business there whose name the records spell out; in the descriptor's city without an address, the one location outside any chain, listed in that city, of a business whose name they spell out, and never for a numbered store. Offices, distributors, and Plaid's location alone never match. A match pins the place and names a merchant whose Plaid name was contradicted or unrecognized.

Annotations also carry tags, a note, a split, a refund link, whether the transaction is someone else's money, and benefit decisions (a confirmation and a hand-chosen benefit, described in [docs/platinum-benefits.md](docs/platinum-benefits.md#review)). A split divides one transaction's amount between categories: its parts share the amount's sign and sum to it exactly in cents, every category total counts the parts, and a split saved for another amount is ignored. A refund linked to a purchase takes that purchase's category and reduces spending. Someone else's money (kind `owed`), set by hand, is neither spending nor income: a purchase made for someone, or what they paid back, Zelle included. Such a purchase keeps `othersSpending`, which Spending counts only when asked for someone else's spending or everyone's. A refund of such a purchase is someone else's too, and so is a card credit the benefit rules pair with it.

People tag transactions without changing any amount, category, or classification. An annotation's people are a hand choice, and an empty list is one too (nobody), so matching never re-tags it. Without one, a payment to or from a person (Zelle, a payment app, or Payments To People) is tagged with whoever's match name its descriptor contains as whole words; the longest match wins, and a tie tags nobody. A trip's companions are saved against the trip's transactions, since trip ids move as a trip grows, and join any trip sharing one. Mac Contacts is read only, for names and photos (`contacts.rs`); nothing from it is stored except the name and card identifier picked.

Category at read time: a manual annotation, else the provider category. A manual category drops the provider subcategory. Each annotation save returns the changed transactions' annotations as they were, and `restore_transaction_annotations` puts them back, which is how the renderer undoes an edit (⌘Z, this session only). A posted transaction inherits the annotation of the pending transaction it replaced (`pendingTransactionId`). Outgoing payment-app transfers (Plaid's `TRANSFER_OUT_TRANSFER_OUT_FROM_APPS`, or Zelle) become "Payments To People" and count as spending. Incoming ones keep Plaid's meaning, a transfer, so a friend paying you back is not income. The committed snapshot keeps provider categories, and React reads classification through `src/lib/transaction-kind.ts`.

Once edits apply and places match, `quality.rs` grades each bank and card transaction's amount, merchant, category, and in-person place by the evidence behind it (statement reconciliation, the issuer's export, a matched business, Plaid's own confidence, where the place came from, an edit) as confirmed, supported, weak, or conflicting; the transaction takes its weakest grade. Activity marks a conflict, and the inspector shows each detail's evidence.

Before edits are applied, `financial_engine::manual` shapes the accounts as the user asked (`manual.rs`): an account with a saved closed date leaves the accounts, holdings, performance, and totals, while its history and activity stay and the renderer gets it as `closedAccounts`; a manual account (one no provider reports, valued by dated entries in settings, a loan counted as owed) joins them with a daily history from its first entry, so net worth history steps up on that day. A statement imported into a manual account also values it: each day it prices the fund units bought (a plan contribution that names units is that purchase too) adds a value, units held times the latest price, an entry wins its own day, and the units show on the account as `statementPositions`, never among holdings, since they have no market price. The account names its statement rows, and rows of a removed manual account are dropped. One entered without a balance is listed without a value, so a statement can be imported into it, and leaves totals complete until it has one. A manual account set to track the S&P 500 (for an index fund with no public price, such as a plan's collective trust) is estimated on every other market day by moving the last observed value before it with the saved benchmark (VOO, dividends reinvested), so its history has the market's shape between statements. `observedOn` lists the observed days, which the account chart marks; after the last one the value is `estimated`, with `balanceAsOf` that day, and the chart dashes it until the next entry or statement replaces the estimate. Net worth and the combined row are summed again from what remains, and the live overlay applies the same adjustment so its totals agree.

`insights::derive` computes these from the typed snapshot, once edits are applied, and never persists anything. A read parses the committed snapshot once into the typed contract; the policy, insights, and Rust's own readers work on that, and it is serialized once for the renderer. `Storage` reuses a derived view while saved data, edits, and the quarter hour are unchanged (every time zone's offset is whole quarter hours, so a benefit window rolling over at midnight anywhere starts a new view):

- `forecast`: recurring bills and income across accounts
- `statement`: card statement dates, from Plaid Liabilities when available, otherwise inferred
- `benefits`: Amex Platinum credits from the rule data in `insights/amex-platinum.json` (see [docs/platinum-benefits.md](docs/platinum-benefits.md)), with posted credits set against the annual fee since its last charge. Another credit card is tracked only when the user assigns it a card product; the spending card needs no assignment. Each calendar benefit carries its periods from the history's first year through this one, each settled as full, partial, missed, settling, or not judgeable; the matches the rules can't settle come as a review queue; and the windows with allowance left, other than subscription credits, come in the order to use them. Each period sums its planned credits, each benefit sums each year, and the card sums each year over the benefits shown (not hidden, and retired ones only while they have credits), with the part captured on purchases made for someone else
- `refundSuggestions`: unlinked refunds from the last 90 days with exactly one purchase they could repay; the transaction inspector offers the link
- `plan`: month-to-date spending, cash coverage, and runway. Cash starts from available balances where the bank reports them, so pending holds count, and a pending bill already in that balance isn't subtracted again
- `attention`: at most three payment-due or cash-shortfall alerts
- `brief`: every need for action (the alerts above, a used card credit about to expire, cash expected to run short, a recurring charge or deposit due more than a week of business days ago with nothing posted or pending, which marking the series' last transaction reviewed dismisses, and cash of $2,500 or more earning 0.5% or less over the last quarter while another cash account the user holds pays 1% or more), which notifications report and Home lists
- `subscriptions`: subscription series with a charge due within a year, each normalized to a monthly cost, and their monthly total. A fixed charge repriced once is still a subscription, forecast at its new price, with the change reported
- `cash`: known cash carried 90 days through the recurring activity that reaches cash accounts, with a range from the amounts each series has posted; unavailable while any cash balance is unknown. It starts from available balances, as `plan` does
- `credit`: utilization per card and across cards with a reported limit, each card's next statement close (issuer cycle for the spending card, otherwise a month after the last statement, marked estimated), and interest charged on the last statement
- `anomalies`: possible duplicates (exactly two identical posted charges from one merchant on one day, at least $10, in the last 60 days) and unusual amounts (far above a merchant's median by its robust spread, with five earlier charges). Marking a transaction reviewed dismisses either
- `trips`: runs of in-store spending away from home regions (regions with a share of in-store purchase days across several months), read from each purchase's resolved place, with the travel and transport bought online on their days. Airline charges and descriptors with a web address bill from the merchant's headquarters, so they never show where you were, and a lone home charge between away purchases a few days apart doesn't end a trip. A trip abroad, more than 800 km from home, or with an airline or airport charge on its days counts as flown. Each trip carries its spending day by day, its rate a day, and its top categories with their shares and what they leave, and each year sums its trips, days away, and spending, so the renderer never divides or adds a total itself
- `people`: each person's tagged transaction count, first and last dates, trips, and what was sent to and received from them through payment apps (a dinner together is not money sent), with what was sent summed across everyone, plus the names unmatched Zelle descriptors carry and who saved they could be: likely when every word of a name is in the other, possible on a first name alone or a shared last name with first names starting alike. `match_contacts` scores Contacts cards by the same rules; nothing matches until the user picks
- `taxes`: this year's and last year's taxable interest, dividends, short- and long-term gains, and wash sales (same ticker within 30 days in any account; a tax-advantaged replacement makes the loss permanent), harvest values, and open wash-sale windows. With a tax profile, an estimate stacked on the user's other income using `insights/tax-tables.json`, a range while dividends are unclassified. A year without tables has no estimate
- `documents`: each pay statement's deposits matched to transactions (same amount, three days before to five after, in the account its printed last four name); each statement row matched to the account's transaction (same signed amount, within three days), which Activity shows as evidence; a W-2 predicted from the year's last pay statement and compared with the real one; the year's income with self-employment tax; and how long each document is worth keeping
- `retirement`: this year's contributions against the limits in `insights/retirement-limits.json` (a year without them has none), read from each transaction's `flow`, the provider's or plan export's own name for the movement. Workplace deferrals count across every 401(k) and 403(b), employer money apart; IRA deposits count by tax year, and one that may be a rollover, or falls before the prior year's deadline, waits for the user. Also tax buckets, each Roth IRA's withdrawable contributions, the savings rate (take-home pay plus deferrals), and invested assets over a year of spending plus planned costs, unavailable before a full year
- `dividends`: each held security's last-year dividend pace, yield, next announced payment, and annual income
- `recurringCheck`: Plaid's mature streams Brief doesn't forecast, for Data health
- `returns`: time-weighted and money-weighted returns per brokerage account beside the benchmark, only where the history records deposits and covers the whole window
- `periods`, `exposure` (`reconcile`): the combined brokerages' statement for each chart window, the one source of the Investments page's period figures: start + deposits − withdrawals + investment gain = end, daily-linked time-weighted ("how your investments did") and money-weighted ("how your money did") returns beside the S&P 500 over the same days, annualized only from a year, a waterfall whose realized gains, dividends, interest, fees, and taxes are booked from the ledger with unrealized change as the plug, and drawdown, volatility, and beta; and how concentrated the holdings are (effective holdings, top-five weight)
- `allocation`: known USD positions by security, instrument kind, and account, and the uninvested cash beside them
- `recap`: for each chart period (the trailing week, month, three months, year, and all history), spending, income, and net, each with its percent change from the period of the same length before it, and the top categories; a period that starts before saved activity is marked partial
- `spending`: for each scope Spending offers (an account, or all of them), whose spending it counts, and each period of a kind (statement, rolling week, month, quarter, year) back to the start of its history plus all of it: what was spent beside the period before cut at the same day, with the change, the daily average, what is pending, and the largest purchase; each category's share and its own comparison, including against what is usual by this point (up to three earlier periods cut at the same day, when history covers two); the current period carried to its end at its pace once a week of it has passed; and each statement's opening and closing balance. The snapshot carries each scope's current period of each kind and its last six months; `get_spending_period` reads any period in full, with the transactions it lists, their merchants, its running total beside the period before (all time's monthly bars instead), and the same narrowed to each category. Navigation stops where the history does
- `changes`: for each chart period (a day, a week, a month, three months, a year, all history), each account's balance change from its daily history and the number of posted transactions; an account whose history starts later is left out and the period says so. Each account type's change is summed over every account and over the counted ones (an unchanged account adds nothing, a type with an uncovered account has none), with the spending cards' apart
- `flows`: for each account, the combined one, and each chart period, posted money in and out, interest, and dividends, and for an investment account its new money and the market's movement; `activityDays` and `activityMonths`: each day's and month's spending and income across every account, for the calendar
- `rollup`: account totals as pages read them: each type's total over every account and over the counted ones, the spending cards apart, positive balances' shares by type, assets and liabilities, investment gains across accounts, the retirement total, net worth without the cards, and each security across the accounts holding it. Each market projection carries its own from live values
- `chartChanges`: each value chart's change over each window, from the line it draws (saved days at noon UTC unless a live point falls on the day, then live points, from the account's start date), read between the points around the window's start. The market stream sends its own with each update, from the lines the renderer holds
- Reports (`reports`, on request through `get_reports`): income, interest, fees, card credits, dividends, realized gains, and cash flow over a chart period or custom days and chosen accounts, each beside the window before only when the history reaches it, by group, by day, month, or year, by account, and with its recurring series; cash flow adds its sources, purchases, and the gap or remainder
- `interest`: each cash account's interest posted in each chart period, with its rate a year on today's balance, and its monthly net flow over all its posted history once that spans two months
- `lots`: open tax lots per position, estimated first-in-first-out from saved trades (each sale's gain is split into short- and long-term parts by the lots it consumed, and each lot carries a tax-if-sold estimate with a tax profile); shares no saved purchase explains make a position partial, and history that contradicts the position has no lots; a fully explained position also has a money-weighted return
- `movers`: the day's change by position from saved prices, not the live overlay
- `accountsTotal`: the total and history without the spending cards (the saved one and any others the user marks), which Money presents on their own. Home's totals and the Accounts "All accounts" view use it; Accounts still lists the cards, apart, and the snapshot's `netWorth` still includes them. The market stream's `accounts` line leaves the cards out the same way; their balances are not market-driven.
- `securities`, `allocation`, `longTermSoon`: holdings merged across accounts with weight and gain, exposure with a concentration flag (one security at 20% or more), and lots turning long-term within 60 days (taxable accounts only)
- `investmentAttention`: only what calls for a decision: a concentrated holding, taxable lots turning long-term with a gain, and taxable losses large enough to harvest, plus the holdings large enough that their earnings dates matter
- `agenda`: every dated item above in one list (payments due, statement closes, credits ending, forecast bills, subscriptions, and income, dividends paid, lots turning long-term, wash-sale windows closing, and trips), through the cash forecast's 90 days, for the Calendar page, the Brief calendar, and the `.ics` export
- `ledger`: read-only queries for Apple Intelligence, capped at 25 rows, including credit cards, taxes, trips, subscriptions, and dividend income from the insights above

`insights/golden.rs` replays results recorded from the former TypeScript implementation.

## Startup and recovery

`Storage::new` locks the app-data directory against a second Brief process, then opens and validates the finance database. Legacy JSON is imported once and deleted only after a valid SQLite backup exists.

If the database is missing, unreadable, or from a newer version, Brief opens a valid retained backup read-only. Writes stay blocked until the user restores it or starts fresh, and original files are kept either way.

The window stays hidden until local reads finish, with a three-second watchdog. Startup never waits on the network.

## Backups and erasure

- **Backups** (`.briefbackup`): SQLite Backup API copies of the whole finance database, excluding Keychain, display preferences, and caches. Export and restore require a single-use macOS authentication. Restore validates the application ID, schema version, integrity, and typed state before installing through the open connection, then advances the revision.
- **Preferences** (`.briefsettings`): a bounded JSON file of display preferences, with no financial data.
- **Erasure:** clears the finance database (bank statements included), every other copy of it in the app-data folder (backups, retained copies, and leftovers from earlier versions), opened statement copies, caches (search's embeddings among them), the object graph, and the readable folder Brief wrote, but keeps Keychain credentials. Removing credentials is a separate action.

## Live market data

When the app is visible and Alpaca is configured, one app-level market service streams held symbols, reprices positions, and sends `MarketProjection` updates, each with its account totals (`rollup`) at the live values and each chart's change at the lines the stream has sent. React applies an update only when its `revision` and `updatedAt` match the committed snapshot. The portfolio's chart also gets its last week at five-minute resolution (`market/intraday.rs`), valued from each holding's bars: only days after the latest trade, when today's shares are the shares held, and each earlier day shifted onto its recorded closing value; a day without one is left out. The saved startup frame draws the same week from cached bars. The week follows the first frame as its own message, always sent (without a week when there is none), and the renderer keeps showing the saved frame's changes until it arrives, so a change read from a partial line is never shown. Past minutes sent as a run (the session's backfill when a stream starts, or coalesced points) each join the lines, but only the run's last carries changes; read as of each past minute, they would walk the change from the open to now. The Holdings chart has its own request-scoped pipeline: it keeps canonical bars separate from latest trades and quotes, and never replaces the portfolio subscriptions.

Earnings (Alpha Vantage) are fetched only on request and spend a local daily budget. A holding's news refreshes when it is opened with saved stories at least 30 minutes old, at most once a minute per ticker, leaving Alpaca's shared per-minute limit to the market stream. A refresh fetches Alpaca (Benzinga) stories and, when an SEC contact email is saved, the company's current and periodic reports from EDGAR (8-K, or 6-K from foreign issuers, and 10-Q and 10-K), whose terms require that contact in every request. Filings appear among the company's stories, so a holding without recent filings shows nothing extra. Rust drops generated filler and analyst ratings and, each time stories are read, tags each story's scope and events from its headline and scores its relevance to the company from 0 to 100 (how few tickers it names, and whether its headline names the ticker or the company's EDGAR name); a story below 40 only mentions the company, as broker notes on peers and roundups do, and never counts as evidence. On launch, and at most every ten minutes, `refresh_portfolio_news` saves the past week's stories for every held stock from one paged Alpaca request and checks EDGAR for the holdings whose filings are oldest, so summaries are ready before a holding is opened. It also reads CNBC's market-section RSS feeds (`providers::feeds`), whose headlines name the causes of market, macro, and theme moves that may name no holding (a report on a private company, say); their tickers are read from the companies a headline names. Each holding's recent Form 4s are read once each (open-market purchases and sales only, with whether a sale was under a 10b5-1 plan). Moves are compared with SPY and a sector fund chosen from the company's SEC industry code (an approximation). The Investments overview reuses this: `get_portfolio_today` prices held positions, SPY, and known sector funds in one Alpaca snapshot to rank each position's dollar effect, `get_portfolio_sectors` groups held stocks by sector, asking EDGAR once about stocks it has never classified. The summary's period report splits the period among the holdings: each day's start-of-day weight times the security's daily return from closes adjusted for splits and dividends, with cash and anything unpriced as one more row so a day's parts sum to its return, Carino-smoothed so the period's parts sum to the period's return. Dollars rank the return drivers and each security's own return the top movers; a holding whose saved trades don't explain its shares is listed as unpriced, never guessed.

`get_investment_summary` describes a returns window for the portfolio or one holding; Rust writes every sentence, and the renderer only styles them. News volume tracks company size, not importance, so nothing ranks by how much was written. One model of "unusual" serves today, the period, and a holding's page: each session's move in layers (below), whose own part is measured in the holding's own typical day (a robust standard deviation), so a volatile stock's ordinary month is ordinary and a steady stock's real move stands out. Each session's record (`summary::sessions`) holds every holding's market, group, and own parts in percent and, when its shares are known, dollars, with the fit behind them (fund, betas, R², window) and the groups that moved; a closed session's record is saved in the finance database, past sessions are filled from a year of closes before the period's first, and today's stays provisional until the close. A period's layers are its sessions' summed, a holding's period kind follows them (own when its own part was at least a typical period, with its group only when the group's part was the larger), and an event's reaction is the holding's own part that session and the next. A beta from under 120 days of history is shrunk toward its prior (the industry fund's beta to the market; for a group, one for the industry fund and zero for another). Each record also counts the session's fund groups, loose groups, and unusual own moves, and Diagnostics shows the rates, so thresholds are measured before they are tuned. Prices on this path are adjusted for splits and dividends. Every day here is a New York trading session (`session`, with NYSE holidays and early closes computed by rule): a story or filing is priced by the first session that closes after it, and a period runs through the latest session that has opened. While that session trades, the latest price stands in for its close; before the open and after the close, today is its close, never a pre-market or after-hours price, and the summary says which. Events come from an event log (`summary::eventlog`) kept with each closed session in six families, each event with its provenance (sourced, observed, or reported), its own time, its source's, and Brief's first save: the ledger's trades and cash activity; corporate actions from the refresh's daily Alpaca read; EDGAR reports by accession number, an amendment folding into what it amends, and chains (an earnings report and its quarterly filing, a deal and its completion) of which only the ends are listed; market-wide days from a reviewed calendar (`summary/eventlog/macro-calendar.json`, Federal Reserve decisions; BLS dates are added only from the published schedule) and published rules (NYSE early closes, S&P 500 rebalances); stories, clustered per company per day with the first report anchoring each; and observed flags (a holding's own move of at least 2.5 typical days, volume twice its median, a 52-week extreme, a fall from the high crossing 5, 10, or 20%). A fact reported twice is listed once: the ledger's credit over the action that expected it, an action or filing over news about it, and a flag only as evidence for the event it measured. Events rank by visible components compared in order (dollars on the portfolio, the holding's own move, the kind's typical effect, whether it was the first report), never a combined score, and on the portfolio each stock supplies at most one. A minor event the stock plainly ignored is left out. A session is quiet for a holding with no sourced event, its own move under 1.5 typical days, and ordinary volume, and for the portfolio when nothing was flagged and its dollars were within one of its typical days. Half an hour after each close, or on the next launch, a close job (`close.rs`) refreshes the portfolio's stories and filings and records that session and any missing in the month before, once per session; it never calls Plaid. The portfolio also names the stocks whose period was unusual for them, whatever their size. Your trades and dividends come from the snapshot; a dividend counts toward a holding only when its activity names the ticker. A company's latest quarter comes from EDGAR's XBRL facts (two requests a week per ticker, only with a saved SEC contact): revenue, the same calendar quarter a year earlier, and net margin, each only when the company tagged it. Each session's layers (`summary::layers`) are each holding's beta times the S&P 500, its beta times its group fund's move beyond the market, and the rest, its own, in dollars. A holding's group fund is whichever sector or theme fund (chips and software apart from Technology) best fits its moves beyond the market in both halves of the past year; its SEC industry code's fund keeps the place unless another fits clearly better. A group moved when its fund's day beyond the market was noticeable for the fund and most members went along; holdings that moved the same way beyond the market together, whose own moves tend to go together, form a group too. The day itself is told in a few lines (`summary::brief`): the portfolio's (or the holding's) move in percent and dollars beside the S&P 500's, then the holdings that led it (up to three moving its way, each at least 15% of its dollars); a day under 0.25% is one line. Up to two headlines (`summary::headlines`) follow, from saved stories between the previous session's close and the next open: for each leading holding, the newest whose headline names it and says it moved its way (or, about one or two companies, says no way), never one that points the other way or only restates the move; then, when the S&P 500 moved at least 0.3%, the newest market wrap saying it moved its way. A quiet day gets none. The renderer warms the portfolio's summary in the background on launch. Each run is logged in memory with its stages' timings and the provider failures it saw (Diagnostics); a part that couldn't load and a year of prices the request's page limit cut short are listed as unavailable with their symbols. Data health warns when saved stories are over two days old or the latest summary run failed, and notes a calibration rate out of range (after a month of sessions, a fund flagged more than three times a month).

## Objects and search

`objects::graph` reads the derived view, the saved documents, and settings into typed objects with stable ids (`kind:key`): accounts, transactions, holdings (`holding:<account>:<ticker>`), trades, documents, statements, people (you are `person:you`), organizations, places, trips, bills, and benefits. An organization is one per name however a source writes it (`organization:<words>`), so merchants, institutions, issuers, and employers that share a name are one object and keep their id across refreshes. Links join them (a transaction's account, counterparty, place, people, transfer pair, refund, bill, benefit, trip), and only between objects the graph holds. Facts are dated statements with their sources (`you` for edits, a provider, `derived`, or document ids), the evidence grade where `quality` gives one, and a tier (Observed or Derived; rules in phase 4 add Explained and Suggested). Your edits become facts with your authority, and pay statements date an employer (`person:you employer`, from the first period to the last).

The graph is built on the first read that needs it, cached with the view, and saved whole to `graph_objects`, `graph_links`, and `graph_facts` when it changes: derived data like market sessions, never in the log, cleared by erasure. A read of one object (`get_object`, the raw view) compares the table row with the graph built from the view and rewrites tables that drifted before answering, and adds the record its provider sent for accounts and transactions.

`search_objects` is one search over every object, plus saved news stories about held stocks (`story:`, at least the relevance that counts as evidence). An in-memory FTS5 index, rebuilt when the graph or the stories change, matches each query word as a prefix of a title, subtitle, or further text, with a date's month and year and an amount's digits searchable too; FTS syntax never reaches it. When words find fewer than asked for, on-device sentence embeddings from Apple's Natural Language framework (`native/EmbeddingBridge.swift`) fill in by meaning above a similarity floor; each text is embedded once and cached in `embeddings.sqlite3`, a disposable cache. Nothing leaves the Mac.

The palette reads it: the Objects tab (`@`) searches every kind, and a first word naming a kind narrows it (`@doc w-2`); elsewhere object rows join the palette's own accounts and holdings rows, and its Activity entries are search's transactions and trades. `/` chips and a field-scoped query (`category: dining`) are filters, not search: the palette applies them to the entries, as the Activity page applies its own. ⌘I on a result, the transaction inspector, or a page's account, holding, or document opens Details, the raw view: facts with their sources, links, the whole record, and the provider's record. Verbs reachable from anywhere are listed once in `src/lib/verbs.ts`, each on a page or an object kind: the palette lists a page's verbs everywhere and an object's under its result (`.` or ⌥↵), and also on its own (`Show taxes…`), where choosing it asks which object, listing that kind before a word is typed (Backspace steps back), and a verb with nothing of its kind to act on says so. `brief://do/<verb>?object=<id>` runs one from Shortcuts or a script. Each opens its page, then runs once the page registers it (`useQueueAction`); only catalog verbs run from a link, and a destructive one still asks on its page.

Coverage: Rust's test places every field of the snapshot and every part of the state (an object kind, or a table the Storage page opens), so a field can't be stored invisibly, and the raw view's test renders every field of every seed object. The route test renders each page with a collector that records what it registers (effects don't run when rendering to a string) and requires every control outside a list row to name an action registered there.

Settings › Backup & data lists every file in the data folder (`inventory`), what each is for, flagged when Brief doesn't know it, and each database's tables, any of which pages read-only; credentials show only that they exist. The readable folder (`data_folder`), off until a folder is chosen, writes `Brief Data/` there in the background after a change or a new day: a README, a CSV per kind (transactions by year) with every field and its facts' sources, `facts.csv`, and linked Markdown pages for people, organizations, places, and trips. It is written beside itself and swapped in whole, can mask every amount, warns when macOS may sync the folder, zips with `ditto`, and is never read back. Brief replaces or removes only a folder carrying its marker, and erasure and turning it off remove it.

## Renderer boundary

`src/lib/api.ts` is the main IPC client; `objects.ts`, `storage-files.ts`, `calendar.ts`, and `contacts.ts` wrap their own commands. The renderer's types are generated from Rust's by ts-rs: `cargo test` writes them to `src/lib/bindings` (one file per type; regenerate from scratch with `rm -rf src/lib/bindings && cargo test export_bindings` after renaming or removing one), and `src/lib/schema/` gives them the renderer's names. Rust's output is trusted, so it is read as typed; runtime schemas remain only where data isn't a Rust type: messages the market stream assembles as JSON, an answer's ledger evidence, settings the renderer edits before Rust validates them, and anything read from browser storage or a file. Links from outside sources are checked in Rust where they enter (news and feeds keep only HTTPS links, filing links are built on sec.gov), and the renderer opens only HTTPS. Synthetic fixtures (`src/data/fixtures/native-*.json`) are checked against Rust's serialization from the Rust side.

React may derive view state (date ranges, filters, chart geometry) but never a total, and never sends a snapshot back. What a view composes, such as an earlier Spending period or a report over chosen days and accounts, Rust computes on request: `get_spending_period` and `get_reports` read the cached view. The period Money opens on is read as each snapshot arrives, so Money opens without waiting. The browser preview reads the view Rust derives from the synthetic seed (`seed-view.json`, by the same `derive_view` as the app), its Spending periods (`seed-spending.json`), its reports (`seed-reports.json`), and its object graph (`seed-objects.json`, which preview search matches by word prefix and the raw view reads); a Rust test writes and checks all four, and `empty-view.json`, which renderer tests start from. A window outside them reads as unavailable there. Edits go through narrow commands: annotations, settings, and account links. Each returns the updated snapshot. Exports (activity and tax lots as CSV, upcoming dates as an `.ics` calendar with no amounts) are written by the renderer from the view and saved through `export_finance_csv`.
